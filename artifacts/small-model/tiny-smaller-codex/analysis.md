**I would test a six-layer Tiny with compact integer state first.** Keep Tiny’s one card layer and one note layer, and cut the deck, preset, and user streams to two, one, and one layers. With int8 weights, 16-bit row scales, and int8 token-shift vectors, I estimate **185,057 parameters, a 239 KB weight file, 803 bytes per card, and 1,315 bytes per note**. Against Small, that is **44% fewer parameters, a 45% smaller int8 weight file, and 40% less state for one card and one note**. The closest trained pruning result suggests a total cost around **+0.5% to +0.6% versus Small**. The combination has yet to be measured. ## Ranked ideas

GPU estimates below are for one 16 GB RTX 5080. CPU estimates are elapsed hours on this host for checks and benchmarks. A new kernel or Rust storage format also requires implementation work.

**1. Prune the context streams and retrain.** The seven-layer context-pruning experiment (SM15) reduced an older 13-layer model from 331,511 to 204,782 parameters. Without training, the cut cost **+4.68% curve and +3.47% instant** on 68 users. After fine-tuning and a long-window cool-down, it cost **+0.36% [+0.16%, +0.54%] and +0.42% [+0.37%, +0.46%]** on 459 users. The larger 724-user readout gave **+0.44% and +0.43%**. It failed its original +0.25% limit. Today’s budget makes that result worth acting on. Applying the same cut to current Tiny gives **six sequential layers instead of twelve**. I calculated **185,057 parameters and 238,585 int8 file bytes** from the released tensor headers. Transferring the larger historical readout to current Tiny gives approximately **+0.56% curve, +0.61% two-head instant, and +0.62% Instant-Only** versus Small. Those are estimates. The cuts interacted in the original experiment, and removing user context can hurt curve particularly hard. A less aggressive eight-layer version would have **224,507 parameters and a 292,401-byte int8 file**. Both retain Tiny’s current card and note state dimensions. [Zero-training pruning screen](C:/Users/jonat/workspace/wt/prune/artifacts/small-model/prune-screen/report.md) · [Trained pruning result in the factory index](C:/Users/jonat/workspace/anki-rwkv/pages/data/factory-curated.json)

The older pruning run logged **3.2 GPU h** on a shorter recipe. I would budget **12–22 GPU h and 1–3 CPU h per variant** for recovery training, the current two-pass cool-down, scoring, and native checks. This is the best candidate for a CPU improvement because it removes whole sequential operations. For scale, the earlier one-card-layer cut improved single-thread native answer replay from **5,777 to 6,332 reviews/s**. Halving the layer count still needs a client benchmark because history reads, encoding, and query work also take time. **2. Keep int8 note matrices and shrink the scales and shift vectors.** The compact integer state experiment (SM47) used one float16 scale per matrix row and one int8 code per token-shift value. On the Muon-trained Small model (SM36), adding both changes to int4 cards and int8 notes moved each head’s LogLoss by less than **0.002%** at the report’s precision on 723 users. Keeping the fork’s existing headers gives an estimated **803 bytes per card and 1,315 per note**, or **2,118 bytes combined**, down 19% from current Tiny. I would expect the three losses to stay near the current Tiny values, allowing roughly another **0.02%** for the mixed state relative to the published int8-state benchmark. This is training-free. Allow **0.25–0.75 GPU h per model and format** for held-out scoring and **0.5–2 CPU h** for encoder parity and native timing. Check float16 scale range and round-trip the state after every answer. There is a more aggressive **card-only** option in the second integer-state experiment (SM49). With one scale per card head and 4-bit card shifts, while retaining the safer note format, I estimate **619 bytes per Tiny card and 1,315 per note**. On the older model the extra cost over the safer mixed format was about **+0.08% curve and +0.13% instant**. I would test it as a separate training-free arm if collection storage is the priority. The card-state drift check (SM78) found the existing int4-card instant cost reached **+0.129%** in the 32–63-review bucket, so a whole-pool mean can hide a maturity-dependent cost. **3. Distill a width-48, one-card-layer Tiny.** The smaller-model design (SM73) specifies **three heads of 16** and **195,949 parameters** with two card layers. Keeping Tiny’s single card layer gives about **184,000 parameters**, an estimated **0.76 MB float32 weight file**, and about **799 bytes per card and 1,183 per note** in the current fork layout. The main square projections would do about **44% fewer multiply-adds**. All twelve sequential layers still execute. The outside research width ladder found that narrowing 80 to 64 channels cost **+0.01% curve and +0.15% instant**, while narrowing 128 to 64 cost **+0.17% and +0.65%**. The repository’s width-48 planning range translates to about **+0.22% to +0.42% curve and +0.48% to +0.99% instant** versus Small after allowing for today’s Tiny gap. Instant is close enough to the limit that the CI could rule this out. The design estimates **6–9 GPU h** for a shorter sliced-weight trial and **36–48 GPU h** for a from-scratch run. I would allow **15–25 GPU h per variant** for a warm start with the current longer finish, plus **2–4 CPU h** for shape, export, and parity checks. Slicing changes layer normalization across channels, so recovery training matters. **4. Train a smaller recurrent state using the PCA result as a starting point.** The training-free state check (SM116) kept **2,373 of 3,392 values** from the show-time retrain (SM92). Its cost was **+0.015% [−0.007%, +0.032%] curve and +0.032% [+0.025%, +0.038%] instant**. The directions came from **94 separate users**. The score covered **629 of 722** and only **51% of rule-pool reviews**. The 93 heaviest users are precisely where repeated compression most needs testing. [State-check result](C:/Users/jonat/workspace/wt/sm116/artifacts/small-model/sm116/sm116-result.md)

The distinction for shipping is that **70% of the values does not establish 30% fewer bytes or a faster review**. The shift-vector projection folds into linear readers. The main recurrent update uses data-dependent decay and removal, so the tested implementation reconstructs and reprojects the matrix. On current Tiny, the eight dense recurrent bases alone would contain **366,592 coefficients**, exceeding the model’s trainable parameter count. I would instead test a native state with, for example, **12 value lanes and 16 key lanes per head**, trained to predict through that smaller state. With current scalar precision and value lanes stored as rows, that design estimates **863 bytes per card and 1,247 per note**. Most trunk weights remain. Transferring the measured PCA penalty would give about **+0.13% curve and +0.22% instant** versus Small, but the native recurrence has a different error and needs its own score. The recorded CPU diagnostic took about **0.5 h to collect directions and 2 h 06 min to score** the capped pool. Budget **15–30 GPU h per trained variant and 3–8 CPU h** for a native prototype’s checks, with additional engineering for the new recurrent shape. **5. Ship int8 weights first and consider group-32 int4 for download size.** The released Tiny two-head model (SM106) already has a **1,270,749-byte float32 file and a 409,483-byte int8 file**. The family wiring selects the float32 file and the native loader can read int8. Selecting int8 would cut the runtime weight file by **68%**. The published family accuracy already includes int8 weights. The loader expands them to float32, so the benefit is download and disk size. The release ZIP also includes reference material and test vectors, which explains how a Tiny ZIP could be larger than a Small ZIP. If the incremental cost over int8 transferred, current Tiny would land around **+0.19% curve and +0.65% instant** versus Small. Stacking that cost on the aggressive depth cut could exhaust the instant budget. Both weight conversions are training-free. Allow **0.25–0.75 GPU h per model and format and 0.5–2 CPU h** for verification. ## First experiment and pre-registered go rule

1. **Fix one architecture and two training runs.** Start from the pre-cool-down weights that produced the show-time two-head cool-down for Tiny (SM124) and the longer cool-down for Tiny (SM115), at epochs 29 and 38 respectively. Apply the six-layer cut above. Give each three recovery epochs and one learning-rate decay over two 32k-window passes of the same 8,000 users. Reuse the existing show-time targets from the show-time big model (SM91s2) for two-head training and the show-time Instant-Only big model (SM99) for dedicated instant training. Budget **24–44 GPU h for both variants**, plus **2–6 CPU h** for checks and timing. The earlier Tiny two-head model (SM106) recovered after an early curve result had triggered its stop rule, so I would make the quality decision after the cool-down. 2. **Score the architecture and the shipping format separately.** Fix the canonical 722 users and matching labels before the run. Score each student once in the published int8 benchmark format, then with the exact proposed weight and state encoding, including a store/read round-trip after every answer. Use show-time intervals, the existing split, and neighbour handling for deleted cards. Report coverage, finite outputs, the longest histories, mature cards, and heavily shared notes. A memory-bounded replay must carry the state across segments. The duration-leak check (SM31) measured an apparent instant advantage of about **0.43%** for an older Small model when its interval included the answer’s duration, enough to change this decision. 3. **Go only if all three upper 95% bounds are at most +1.00%.** For each paired user-bootstrap draw, recompute the review-weighted LogLoss of the proposed shipping model and its matching Small reference, then calculate `100 × (Tiny / Small − 1)`. Use 2,000 draws, seed 0. Apply the rule independently to two-head curve, two-head instant, and dedicated instant. Use the published Small references for the stated budget and verify the decision against Small’s actual fork precision as well. Missing heavy users, nonfinite predictions, or a crossing CI leave the affected variant experimental. My proposed engineering gate is **at most 200,000 parameters and 2,200 serialized bytes for one card plus one note**, with median native single-review CPU latency within **5%** of current Tiny or faster on the same fixture. Record card and note bytes separately, median and p95 query/update latency, and one-model and paired rebuild time.

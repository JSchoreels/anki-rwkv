# R01 E33 update anatomy and idea scouting (diagnostic, no training)

Purpose: find new R01 speed candidates after the 0034–0039 misses. These are focused diagnostics on real E33 batches, not optimization iterations: no training run, protocol, smoke or reviews/s measurement was produced, and nothing here changes the accepted 0033 reference. The resulting tracks are F48–F57 in [GPU_OPTIMIZATIONS.md](../../../docs/GPU_OPTIMIZATIONS.md).

Provenance: Git `722f0427032a542ae0f6b4dd553c791fa1cd2f93`, clean tree (diagnostic scripts were outside the repository while running; copies are preserved in [scripts/](scripts/) and [../r01-padding-structure-v1/padding_stats.py](../r01-padding-structure-v1/padding_stats.py)). Torch 2.9.1+cu128, CUDA 12.8, CuPy 14.2.0, driver 617.14, RTX 5080; run 2026-10-12 with no other Python/GPU job active. Model: Expertium, fresh seed-2025 weights, BF16 child, accepted E33 flags (exact shift/index/GroupNorm, four-row exact recurrence with 32-step checkpoints, stream launches, shared shift orders, prefetched rows, sync-free loss), deterministic algorithms on, one main thread. Batches: R01 cohort user 2723 (offset 0, 65,536 reviews, 512 chunks; "large") and user 609 (18,812 reviews, 147 chunks; "medium"), seeds 2025 + user + offset. Timings are synchronous single-update wall times (synchronize before and after), not training throughput.

## Findings

| Question | Result | Evidence |
|---|---|---|
| Where do the ~3,000 `fill_` launches per update come from? | Deterministic mode's `torch.utils.deterministic.fill_uninitialized_memory` (default on) NaN-fills every `empty`/`empty_like`/`empty_strided` result: LayerNorm/GroupNorm forward and backward, dropout, WKV backward outputs, lerp and shift backward. 2,969 of 2,969 attributed fills on the large update sit directly under an allocation. | [result.json](result.json) `fill_memset_sources` |
| Is turning that fill off exact, and what does it save? | Loss and every parameter gradient bitwise equal on both batches. Launches per large update: `cudaLaunchKernel` 11,545 → 8,943 (`fill_` 2,969 → 214); medium 7,852 → 6,081. Median synchronous update: large 307.09 → 292.72 ms (−4.68%), medium 118.45 → 108.99 ms (−7.99%), four alternating repeats of four updates each. | [ab-fill-skip.json](ab-fill-skip.json) |
| Are row-select gradients from padded sources exact zeros? | Yes: 0 nonzero, 0 negative-zero and 0 non-finite values over 274,088 + 41,155 padded sources (10.1 M BF16 values). `rows_backward` starts each float sum at +0.0f, so ±0 terms are identities; skipping index −1 sources gave bitwise-equal outputs on all 28 calls and loss/gradients equal in the A/B. | [result.json](result.json) `row_select_calls`; [ab-fill-skip.json](ab-fill-skip.json) |
| What does skipping padded sources save? | Row-select backward device time 8.465 → 5.390 ms per large update (largest call 2.00 → 0.37 ms, 104,584 padded sources); medium 2.355 → 2.083 ms. Synchronous update −1.00% (large, fill off) and within noise (medium). | same |
| How much padding and how many layer instances? | 21 of 167 sampled E33 updates: padded/real positions 1.32 (24.4% padding; card 1.19, deck 1.67, note 1.33, preset 1.35, global 1.07). Mean splits per update card 3.48, deck 2.95, note 4.00, preset 1.29, global 1 → 34.1 layer instances for 14 layers (large example 44, medium 30). Each review contributes about 1.88 positions per stream by model construction. | [../r01-padding-structure-v1/sample-every-8.json](../r01-padding-structure-v1/sample-every-8.json) |
| Where does large-update device time go? | 237.0 ms of kernels (profiled) versus 308.1 ms synchronous wall; medium 65.5 versus 124.4 ms (host-bound). WKV kernels 114.5 ms (forward 15.5, backward 99.0). T=256 splits (deck 742 rows, preset 869, global 512) take 6.4, 7.9 and 5.5 ms per backward call, 6–9× their forward. | [result.json](result.json) `wkv_kernels_ms` |
| How much could concurrent splits overlap? | Summing, per (stream, layer), only the slowest split instead of all splits lowers WKV backward 99.0 → 78.1 ms and forward 15.5 → 12.9 ms on the large update (upper bound for recurrence overlap only; medium 24.2 → 22.1 ms). | [result.json](result.json) |
| Do other recurrence tilings help? | All of rows 1/2/4/8 at tile 32 and rows 4/2 at tile 16 and rows 4 at tile 8 were bitwise equal to production on nine real shapes. Production (rows 4, tile 32) is near best; rows 8 cut some backward calls by 3–20% but slowed forward. | [wkv-shapes.json](wkv-shapes.json) |
| Is the recurrence backward occupancy-bound? | No. Production backward uses 80 registers (3 blocks/SM), 17,152 B shared and 1,024 B local per thread. Register caps 72/64/56/48 stayed bitwise equal but were slower or equal (742×256: 6.82 → 6.92/7.24/8.42/10.15 ms). Per-step latency (local memory, barriers) is the limiter. | [wkv-regcap.json](wkv-regcap.json) |
| Is TorchScript fusion (`jit_optimize`) usable? | No for varying shapes. First occurrences of each shape took 1.5, 10.3, 13.9 and 2.5 s; steady state was 283–285 versus 293–305 ms (large) and similar medium. Loss equal, gradients not bitwise (max relative difference 2.3e-7). | [jit-optimize-0.json](jit-optimize-0.json), [jit-optimize-1.json](jit-optimize-1.json) |
| Per-user bookkeeping cost? | `sampled_tree_rss` 4.5 ms median and `atomic_json(result.json)` 0.8 ms per user, about 0.4 s per 80-user run (≤1%), on the main thread. | measured inline; not retained as JSON |

Limits: two batches, synchronous timing and one machine state; effects in the asynchronous training loop (deferred reads, prefetch) remain unmeasured. Full-run parity, the 2%/5% gates and loss ceilings still apply to each candidate.
